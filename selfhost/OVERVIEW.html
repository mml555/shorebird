The idea

What it is — and what it isn't

Shorebird ships five things: a CLI, a wire protocol, a modified Flutter engine, a Rust updater, and a hosted backend. Four are open source; only the backend is closed — and it's the one piece that makes self-hosting impossible. This project replaces only that backend with a compatible one, and consumes the rest as published, open-source artifacts.

It is not a clone of the engine or updater — reproducing those is Shorebird's entire business. We stand on their open-source runtime and own the control plane around it.

*Two closed pieces replaced: the hosted backend (fully reimplemented here) and the build-time CDN routing (mirrored locally). The engine + updater are consumed as open-source prebuilt artifacts — the updater is also vendored and builds from source.
Architecture

The pieces and who owns them

  • ▹Ours: the backend (this server), Postgres + MinIO, and the build-time CDN mirror.
  • ▹Consumed (open source): the CLI, the protocol DTOs, the modified Flutter engine, and the Rust updater (also vendored + built from source in vendor/updater).
End to end

How a patch actually reaches a device

The trust boundary

A patch becomes device-visible only if: its artifact is verified, the patch is ready (not invalidated), an active promotion makes this client eligible on the requested channel, and its number exceeds the client's. Any ambiguity → no patch.

Rollback

Withdraw stops offering a patch to new checks. A rollback also lists its number in rolled_back_patch_numbers, and installed devices revert on next launch — verified on Android and macOS.

Independence

How far it stands on its own

Runtime proven

Devices talk only to your server — no api.shorebird.dev in the code-push path. Confirmed on real hardware via network capture and the updater's own logs.

Build-time proven

The CDN mirror serves the engine + aot-tools + patch tooling. Verified cache=MISS→HIT: first build warms from GCS, every build after is local, zero Shorebird contact.

Updater from source builds

Vendored at a pinned commit in vendor/updater and builds with cargo to the linkable libupdater. Cross-compile targets installed.

Engine from source scoped

Documented in ENGINE_BUILD.md; needs a build farm (depot_tools, ~100 GB). Until then the prebuilt engine is consumed via the mirror — the recommended path.

Run it

From zero to a working control plane

# 1. one-click: generates secrets, starts everything, prints your URL + API key
cd packages/code_push_server
./setup.sh                      # or: ./setup.sh --domain cps.you.com  (HTTPS)

# 2. point the unmodified CLI + device at it (one base_url covers both)
export SHOREBIRD_HOSTED_URL=<url setup.sh printed>
export SHOREBIRD_TOKEN=<api key setup.sh printed>
# app shorebird.yaml → base_url: <that url>

# 3. ship — exactly the normal Shorebird workflow
shorebird release android && shorebird patch android
A single base_url redirects both the CLI (build side) and the on-device updater (runtime side) — no engine rebuild, no forked app.
Handoff

What remains — and why it's external

Everything achievable in this environment is done. What's left needs resources outside it, not more code:

  • ▹Windows / Linux device tests — need those build hosts (no cross-build from macOS). Server needs no change. host
  • ▹Real Google / Microsoft login — needs your OAuth client credentials; broker is built & stub-verified. See IDP_SETUP.md. creds
  • ▹iOS at scale — a registered bundle id + provisioning under your Apple team. See IOS_ONDEVICE.md. apple
  • ▹Engine from source — a build farm with depot_tools + ~100 GB. See ENGINE_BUILD.md. infra
The standing risk is compatibility drift, not missing features: we consume Shorebird's evolving engine/updater, so revisions are pinned in compatibility.yaml and upgrades are gated on re-running the verification suites.
