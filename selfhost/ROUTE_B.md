## SDK instance members: what a patch may call (device list AND this release)

A patch that calls an instance member of a `dart:` class binds it by selector
when it runs, so it works only if THIS release kept that member. The CLI accepts
such a call only when both hold:

1. **The device-measured list.** The member is in `routeBSdkMeasuredAccepted`
   (`packages/shorebird_cli/lib/src/route_b_sdk_measurements.dart`), generated by
   `evidence/sdk_instance_members/gen_dart_lists.py` from the iPhone 7 (iOS
   15.8.8) matrix of PR #216 on a Flutter release cut at engine cell `2fc41d3f`
   (data in `engine/route_b/device_run/sdk_members/result/`). A key is
   listed only if every probe resolved, there was more than one probe on more
   than one runtime class, and each runtime class maps to a VM class. Keys that
   throw `NoSuchMethodError`, crash, never ran, or are thin are refused. A
   tear-off key (`...#tearoff:name`) is accepted only when its call form (the
   same key with `#tearoff:` replaced by `#`) is accepted too, in the CLI and in
   the generator: the device probe of a tear-off creates the closure and never
   calls it, so it proves nothing about calling it (`String#endsWith` aborts on
   the phone). This took 24 keys off the list (118 to 94): 5 typed
   (`Stream#listen`, `Iterable#any`, `List#sort`, `Set#remove`,
   `String#endsWith`) and 19 `dynamic#tearoff:*`. A probe that calls the closure
   needs a new device run (follow-up).
2. **This release's own snapshot.** The release's `route_b_snapshot_profile.json`
   (already uploaded and hash-checked; no new artifact) must resolve the member
   with real code (not a `LazyCompile` stub) on EVERY instance class that can
   stand in for the declared type. For a declared type T the CLI takes the
   classes of that name in `dart:` libraries (classes are keyed by library as
   well as name, so a user's own `_List` never stands in for the SDK's), walks
   the release's own `super_type_` and `interfaces_` edges to every subtype
   present in the snapshot, keeps the instance classes, and requires the
   member to resolve on each, on the class or a super class. An instance class
   reaches `Object` and is either seen allocated (it owns a `[Stub] Allocate`
   stub or the snapshot holds a const instance of it), with or without code
   of its own, or has real code and may be concrete: a leaf, or a `dart:` base
   class the VM allocates with no stub (`route_b_sdk_base_classes.dart`). The
   profile does not mark abstract classes, so this is a heuristic that errs
   toward refusing; #253 replaces it with abstractness from the release kernel. A missing, unreadable, malformed or digest-mismatched
   profile (the digest compare ignores case) refuses, as does a super chain that
   loops or is cut short. Dynamic tear-offs (`dynamic#tearoff:x`) are checked
   against every instance class in the snapshot.

**Stricter since PR #252 (#249).** Base classes the release allocates, and
classes allocated with no code of their own, are now checked too; before, only
leaves with code were. Patches the CLI used to accept can now be refused. The
largest group is `Future.then`, `catchError`, `timeout` and `whenComplete`
(called or torn off) in any Flutter app with an `AnimationController`: such an
app allocates `TickerFuture`, which keeps none of them, and a `Future` value
can be one at runtime. The refusal names the class and says why. What to do:

- If the value is never a `TickerFuture` (it comes from `async` code, `http`, a
  plugin), `await` it instead, with `try`/`catch` for `catchError` and
  `try`/`finally` for `whenComplete`. `await` of a `Future` made by `async` code
  or the SDK goes through `_Future._thenAwait`, not `then`. `await` of a
  `TickerFuture` calls its `then` (`_SuspendState._awaitUserDefinedFuture`), so
  it is not a way out when the value can be one.
- `timeout` has no `await` form. Ship the change in a new release: a release
  built with the code that calls the member keeps it.

A member named by the release's own interface still passes, as before. The
interface names only the members `--sdk-members` lists, which a release builds
in two tiers:

- **Always kept (default):** `print`, `DateTime.now`,
  `DateTime.millisecondsSinceEpoch`, `identical`, plus 53 cheap members (`Map`,
  `Set`, `String`, `num`/`int`/`double`, `Iterable.isEmpty`/`isNotEmpty`/`join`,
  `List.clear`/`sublist`). Cost: +1.8 % of the AOT size (airgap app, baseline
  6,560,960 B).
- **Opt-in, 21 heavy members:** `Iterable.any`/`where`/`map`/`toList`/
  `firstWhere`/... and `List.addAll`/`sort`/.... Each costs about +2 %, because
  the typed-data list mixins each get their own copy. All 74 members together
  are +10.7 %. A release keeps them only when the checked-in `shorebird.yaml`
  sets `keep_sdk_collection_methods: true` at release time. Without it a patch
  that calls one is refused, and the refusal names the key.

`--allow-unchecked-sdk-calls` skips check 2 (the per-release snapshot check) and
the analysis-19 gate. It never skips check 1: a member that is not on the device
list is refused with no flag and no release setting that unlocks it; only a
device measurement added to the list does. Its use is recorded in the patch
metadata (`allow_unchecked_sdk_calls`).

**Caveats.**
- "Safe" was measured on ONE app at ONE cell. A member the Flutter framework
  itself uses is expected in every Flutter release, but that is not proven per
  release; per-release evidence (R4) is the real fix.
- The profile check is necessary, not sufficient: `List.sort` and
  `Iterable.contains` on a `List.filled` list have real code and still abort on
  the device. That is why check 1 comes first.
- Runtime classes the matrix did not measure (`MappedIterable`, a user's own
  Iterable) are not proven by it.
- Calibration: `test/src/route_b_sdk_calibration_test.dart` replays every
  measured (key, VM class) pair against the 2fc41d3f profile
  (`evidence/sdk_instance_members/profile_2fc41d3f.json.gz`); each must resolve.
  One group differs and is explained there: `int` `&`, `<<` and unary `-`:
  the device probes used plain `int` operands, which the patch's bytecode
  compiler turns into `BitAndInt`, `ShlInt` and `NegateInt` opcodes with no
  lookup (`pkg/dart2bytecode/lib/recognized_methods.dart`). It does so only
  when both operands are statically exactly `int`: a `T extends int` operand
  is a call looked up by name, and `_Smi`/`_Mint` have no such member on
  2fc41d3f. The analysis does not yet say which static types a call site has,
  so these keys are checked like any other and refused on this release. (The
  same holds for every operator, `num` ones included: no key is skipped.)
  Analysis 21 closes that: the analyzer asks dart2bytecode's own
  `RecognizedMethods` about each operator site and marks an instance
  reference `inlined: <Opcode>` (several opcodes, when the key has int and
  double sites, are joined with `|`) only when EVERY site of it in the body is
  an opcode. The CLI accepts the flag only on the 16 operator selectors of
  `int`/`double`/`num` with an opcode that selector can have, only from a
  document of analysis 21 or later (20 predicted it without the signature
  types below and is not believed), and then asks neither the device list nor
  the snapshot for that reference; anything else it ignores.
  The analyzer decides on the PATCHED kernel, but dart2bytecode compiles the
  producer's lowered slice, so correctness does not rest on a list of
  rewrites. Three layers: (1) the analyzer clears `inlined` in a body with a
  `super.` use (the producer emits `as dynamic`); (2) the analyzer reports the
  INFERRED parameter and return types (`signatureTypes`) and the producer
  writes them into the lowered signature where the source omitted them (an
  override's `f(a)` takes `a` from the overridden member; a top-level function
  overrides nothing), refusing the target when the type cannot be named in the
  replacement library; (3) after compiling, the producer has the cell's
  analyzer read the payload (`route_b_analyze --scan-bytecode`) and drops the
  flag of any reference whose selector the bytecode still calls by name
  (InterfaceCall, DynamicCall, ...); a payload that cannot be read drops every
  flag, and so does one with a call line the scan could not parse (the scan
  counts them: `unparsed` must be 0). Dropping the flag means the normal check,
  which normally refuses. A type written into the lowered signature is refused
  when an unprefixed import of the target library exposes the same name. The
  analyzer tests (`inlined_ops_test.dart`, `external_uses_test.dart`) and
  `inlined_ops_qualify.sh` need the engine's Dart and run in no CI job: the
  cell mint is the only place they run, and the mint is also the first run of
  the producer's scan against a real analyzer. `inlined_ops_test.dart` fails
  when the CLI's `inlinedOpcodes` drifts from dart2bytecode's tables.
  `coverage/inlined_ops_qualify.sh` proves the flag: it runs the real
  producer and a real dart2bytecode over every member of
  `inlined_ops_fixture.dart` (as top-level functions and as instance methods,
  TFA on, plus the `super.` cases), and compares per reference and per
  selector, in both directions (flagged iff the bytecode has no call to that
  selector). It fails on a mismatch, on a refused target, and on a run that
  compared too little. The cell mint (`mint_route_b_cell.sh`) runs it against
  the cell's own `dart2bytecode.aot`; run it the same way
  (`--compiler-aot ... --runtime ...`) before publishing. A cell built with
  an older analyzer behaves as before.
- A dynamic call (`declaredClass == null`) is checked against every instance
  class of the snapshot; a declared type with no class in the snapshot, or only
  in another library, is refused.
- A patch cannot add a class, so the receiver's class is always one of the
  release's: `analyze_coverage.dart` refuses a class that is not in the release
  (the `declaration` category, "a patch cannot add one") and a member of it
  (`_instanceHelperReason`, 'a member of `X`, which the release does not
  have'). A `class Ring extends ListBase<int>` calling `add` is refused on the
  document alone (`route_b_coverage_test.dart`).
- The profile check does not cover a tear-off's call: it looks up the member
  by its bare name, so a tear-off is judged exactly like its call form, and a
  member that has code and still aborts when called (`List.sort` on a
  `List.filled` list) passes it. Before
  the call-form rule, 22 of the 24 tear-off keys it removed were already
  rejected by it on this profile (all 19 dynamic ones, `Iterable.any`,
  `List.sort`, `String.endsWith`); `Stream.listen` and `Set.remove` were not.
- On the 2fc41d3f counter release's own profile, 10 of the 94 accepted keys
  are rejected (84 pass; the calibration test pins the exact set and the
  profile's sha256): `Iterable` `first`/`toList`/`toSet` (including
  tear-offs) and `List.reversed` (a subtype in the snapshot lacks them:
  `_ConstSet`, which has 11 constants in the image, and the typed-data lists,
  which the VM allocates), `num.~/`, `int` `&`/`<<`/unary `-`.
  The leaf heuristic is conservative: a class counts as an instance class when
  it is a leaf with real code, so a snapshot-only class a program never builds
  (for example `_ExternalFloat32x4Array`, whose only factory throws) can still cause a refusal.

## The capability statement, as of 2026-08-11

> **Automatic iOS Dart code push works end to end without Shorebird's private
> AOT linker.** `shorebird release ios` -> edit one function -> `shorebird patch
> ios` -> control plane -> updater download -> inflate -> install -> lifecycle
> promotion -> native pre-main activation -> patched Dart running -> relaunch
> still patched -> rollback to pristine AOT. Nothing manual in between, at
> +4.5 % size and +0.3 % median frame time with zero added jank.
>
> **Current proven producer surface: a single-function replacement whose every
> reference resolves inside the release's declared retention** — literals, the
> target receiver's own members (public, and release-private instance state
> through the G3.6b/P2 capability path), retained public app symbols, and named
> SDK members carried in the release's dynamic interface.

**This does not establish arbitrary dependency reach from replacement bytecode.**
A reference binds only if the release retained it: the dynamic interface is
declared by a kernel prepass at release time, and a private member additionally
requires a grant in that release's capability manifest. Anything outside that
closure has nothing to bind against. Independently, the producer refuses compound
writes, `super`, cascades, `this` used as anything but a path to a member, and
replacement signatures taking parameters — by design, before a patch exists.
"Ordinary Dart patches work" remains too strong.

The closure rule is the boundary; "a self-contained body" was the historical
approximation of it, and it stopped being accurate once retention could be
declared from a kernel prepass. See the widening ladder below, then the frozen
instance surface for what is refused by design.

> **Superseded, 2026-08-13, and it had gone self-contradictory.** This section

### The producer reaches rung C on its own — CLOSED ON DEVICE 2026-08-11

Rung C was proven with a HAND-WRITTEN replacement, because the entry-point
contract takes a static function and the app declares an instance method.
That gap is closed: engine `3568f73c`, release `19.0.0+1`, iPhone 7. The
fixture says

```dart
class RouteBThing {
  String label = 'NEW-C1';
  @pragma('vm:never-inline')
  String value() => label;      // nobody writes `self`
}
```

and `shorebird patch ios` shipped

```dart
String value(RouteBThing self) => self.label;
```

byte-identical to the hand-packed payload rung C proved. `OLD` -> `NEW-C1` ->
relaunch `NEW-C1` -> rollback `OLD`. Evidence `evidence/lowering_*`.

**Kernel decides meaning; source text only supplies syntax.** The analyzer
reports which accesses are receiver-based, what they resolve to, and where the
identifier starts — so a local `label`, a top-level `label` and `Cls.label`,
which are different Kernel nodes, are never touched. The producer reads the
source only to answer the one question the tree cannot: whether `this.` was
written, since the synthesized `ThisExpression` carries the access's own offset.
Anything else — a call, a setter, `super`, a private member, unusual spacing
around `this` — is refused, not guessed at.

### The call form — CLOSED ON DEVICE 2026-08-11

Engine `ebcf143f`, release `20.0.0+1`, same phone. `String value() => helper();`
shipped as `String value(RouteBThing self) => self.helper();`, and the
interpreted replacement dispatched into the release's own AOT `helper()`:
`OLD` -> **`NEW-C2`** -> relaunch -> rollback `OLD`. Evidence `evidence/call_*`.

Kernel puts an invocation's offset on the identifier exactly as it does a read,
so the lexical edit did not change. What changed is which invocations the
analyzer vouches for: public, zero-argument, receiver-bound.

**Arguments need no gate.** The edit inserts a prefix immediately before the
identifier and copies everything after it verbatim, so positional, named,
generic and nested argument lists cross over untouched. `helper(label)` is two
reported accesses and becomes `self.helper(self.label)`.

A note here previously claimed the AOT kernel cannot be trusted about arguments.
That was measured, but on a probe that compiled without a dynamic interface —
which no release does. `--aot` eliminates a constant-only parameter *only* when
the library is not retained; with the interface a release always declares, the
parameter and the argument both survive. Corrected in the engine README; the
lesson is about probe fidelity, not about Kernel.

**Argument-bearing calls are device-proven too** — engine `8ebaad05`, release
`21.0.0+1`. `String value() => tagged('ARG');` shipped as
`String value(RouteBThing self) => self.tagged('ARG');` and the interpreted
replacement passed its argument into the release's compiled method:
`OLD` -> **`NEW-ARG`** -> relaunch -> rollback `OLD`. Evidence `evidence/arg_*`.

**Both `this.` spellings are device-proven** — release `21.0.0+1`, patches 2 and
3: `this.label` read `NEW-C1`, `this.tagged('ARG')` read `NEW-ARG`, and the
rollback returned `OLD`. Evidence `evidence/this_*`. They are the same Kernel
nodes as the bare spellings but a different lexical edit — `this.` replaced
rather than a prefix inserted — so they were their own items.

`tagged` and not `helper` in that second patch, deliberately: on release 21
nothing names `helper`, so the prepass would shake it out before retention is
declared and the patch would have failed for a retention reason rather than a
lowering one. The lexical edit is identical either way.

### Receiver writes — CLOSED ON DEVICE 2026-08-11

Engine `aa915584`, release `22.0.0+1`. `String value() => slot = 'NEW-SET';`
shipped as `String value(RouteBThing self) => self.slot = 'NEW-SET';`:
`OLD` -> **`NEW-SET`** -> relaunch -> rollback `OLD`. Evidence `evidence/set_*`.
The value shown is the assignment's own result, so a write that silently did
nothing would have read `UNSET`.

A write is the same lexical edit as a read — Kernel puts `InstanceSet`'s offset
on the identifier — and the right-hand side crosses over as source text. A
receiver use inside it is its own access: `label = label + 'Y'` becomes
`self.label = self.label + 'Y'`.

**The compound refusal is derived, not enumerated.** Measured on real Kernel:

```
label += 'X'        SET @240  GET @240     one token, two jobs
count++             SET @269  GET @269
maybe ??= 'Z'       GET @315  SET @315
label = label + 'Y' SET @447  GET @455     two tokens, two offsets
```

So the rule is *two accesses at one offset*, which covers compound assignment,
increment and if-null uniformly — including forms nobody has enumerated — and
leaves the legitimate self-referential write alone. Without it the producer
would emit `self.self.label`.

Supported so far: `label`, `this.label`, `helper()`, `this.helper()`, the same
calls with arguments, and `slot = expr` / `this.slot = expr`. Refused: cascades, `super`, setters, private members,
and any access kind the producer does not recognise.
`probes/lowering_matrix.sh` pins all of it against real Kernel, 17/17;
`probes/lowered_forms.sh` runs seven spellings end to end on the host, 14/14.

### The instance surface, FROZEN 2026-08-11

Widening stops here. Not because the next rungs are hard, but because the ones
after this one stop being the same kind of problem.

Everything above is one transformation: **rewrite the receiver, preserve the Dart
expression.** Kernel says which identifier is receiver-bound and what it resolves
to; the source supplies the syntax; the producer inserts or replaces a prefix at
one offset and copies the rest verbatim. Nothing reconstructs Dart semantics,
which is why arguments, named arguments and nested expressions cost nothing to
support — they were never interpreted.

#### Supported, for an instance target

| form | example | lowered |
|---|---|---|
| public read | `label`, `this.label` | `self.label` |
| public call | `helper()`, `this.helper()` | `self.helper()` |
| public call with arguments | `helper('a', b: f(1))` | `self.helper('a', b: f(1))` |
| simple public write | `slot = expr`, `this.slot = expr` | `self.slot = expr` |
| receiver use inside an argument or RHS | `helper(label)` | `self.helper(self.label)` |
| the replacement's own private helpers | | carried in the payload |
| release-private instance **read** | `_secret` | `self._secret`, granted via G3.6b/P2 |
| release-private **getter** call | `_codePatch` | `self._codePatch`, granted via G3.6b/P2 |
| a target method **on a private class** | any of the above, inside `_Foo` | receiver written as `_Foo self`, resolved by `--resolve-private-names-in-library` (G3.6c, G3.6e) + `class: '_Foo'` retention (G3.6d) |
| a target method with **its own required positional parameters** | `tagged(String x)` | `tagged(Self self, String x)` — G3.7, patch `0006`. Device-proven on releases 37 and 38 |

All device-proven; see the rung sections above for engine, release and evidence.
The private read closed on release `31.0.0+1` patch 2, 2026-08-13: the producer
emitted exactly `String value(RouteBThing self) => self._secret;` and the phone
displayed `NEW-PRIV` (`evidence/releases/31/`, commit `c7661317`).

G3.7 closed on device 2026-08-13, all four of its shapes: release 37 proved a sole
positional `String` transfers and is observable in the replacement body; release 38
proved two arguments arrive **in declared order keeping their types** (`PARAM-a-7`,
where a transposition renders the visibly wrong `PARAM-7-a`), with the sibling
method `paramValue` unmoved as the per-method-replacement control. Its `named` and
`opt` arms were **refused at patch time on device**, exit 70, no container, each
citing its own parameter shape rather than "not in the interface"
(`evidence/releases/37/verdict.txt`, `evidence/releases/38/verdict.txt`;
gate `plans/G3.7-param-abi-device-gate.md`).

**READ, not access.** A private **write** (`_secret = x`) has NOT been
device-proven and this row must not be read as implying one. The target's release
never reads `_secret` either, which is what made it a real test of retention
rather than of use.

#### Refused by design — not "not yet"

| form | |
|---|---|
| compound writes | `+=`, `-=`, `++`, `--`, `??=` |
| `super` GETTERS and SETTERS | `super.x`, `super.x = …`. A zero-argument `super.foo()` is HOST CERTIFIED under narrow-v1 (see below) but reaches no shipped release, because no published cell implements it |
| private **method** calls taking arguments | `_hidden('x')` — host-proven only. Private reads and private GETTER calls are supported and device-proven; a getter is a `Procedure`, so this is expected to work, which is exactly why it needs measuring rather than assuming |
| cascades | `this..foo()` |

| a replacement whose signature takes NAMED parameters | the `ArgumentsDescriptor`'s names must match and that is unexercised |
| a replacement whose signature takes OPTIONAL positionals | their defaults live in the AOT function the replacement stands in for, and nothing carries them across |

### A class or extension member's own statics (class scope)

A class or extension member is carried as a top-level function, so an unqualified
`k` that meant the class's `static k` would be looked up among top-level names,
and a same-named top-level `k` would win with no diagnostic. The analyzer
reports `enclosingScope` for each class or extension member the patch carries:
every use of an own static written without a qualifier, placed from the front
end's token stream, and the producer writes `Class.` in front of it. What it
cannot place it refuses: a class type parameter in an instance body, an own
static spelled inside a folded `const` collection or constructor call, a
parameter or local named like a static, an annotation naming one, a mixin
application copy, an instance member of an extension type, and an entry whose
name a carried helper also spells. The refusals over `const` arguments are broader than
the hazard (they refuse even with no top-level twin); write `Class.name`.

**Extension instance members (analysis 22).** Kernel compiles `String get stars
=> glyph * this` in `extension Stars on int` to the static `Stars|get#stars(int
#this)`, which is the key the release's snapshot and the replacement's selector
use, so a replacement is the top-level `String stars(int self) => Stars.glyph *
self` and needs no engine change. The analyzer reports `extension` and
`receiverType`, and `this`, `$this` and `$a$this$b` become `self`/`${self}`. A
call of a sibling made as `sibling()` or `this.sibling()` is written
`Stars(self).sibling()`, so it cannot resolve to another extension in scope. A
call on something built from the receiver (`this..m()`, `this?.m()`,
`(this + 1).m()`) is not rewritten and is refused. Also refused, with the
reason: a generic extension, an unnamed or private extension, an extension type,
an on-type that is not a public class of dart:core or of the target's library, a
setter or operator, optional or named parameters, member type parameters, a
tear-off of a sibling, a member that spells the extension's own name as a
parameter, local or value (it would capture `Stars(...)`/`Stars.`), a key with
no `lowering` or whose lowering names no extension, and any document older than
22. A refusal of an extension member on an older cell comes from that cell's own
analyzer; the producer never sees an `extension` field below 22. Nothing here
was run on a device.

**For-in receivers (analysis 23).** `for (final s in shapes)` asks the runtime
receiver for `iterator` by selector, so the per-release check asks every class
that can be that receiver whether its snapshot has compiled code for it. Up to
22 that was every `Iterable` of the release, so a loop over a `List` was refused
whenever some other `Iterable` (Flutter's `ObserverList`) had no compiled
`iterator`. From 23 the analyzer names the class of the iterable's static type
(`receiverLibrary`, `receiverClass`) on the `Iterable.get:iterator` reference
only, and the CLI asks only that class's subtypes for `iterator`, which still
include every `List` the app wrote, mixin applications included. Only that one
question narrows: the loop's `Iterator.moveNext` and `Iterator.get:current`
references, and the VM classes measured on the device for `iterator`, are
checked as before, so a loop over a `List` can still be refused by them. An
iterable typed `Iterable` itself, `dynamic`, nullable, `FutureOr`, a type
parameter or an extension type names no receiver and is checked as before, and
so is a class the release's snapshot does not hold. A refusal names the
receiver ("`Iterable.iterator` over a `List`").

A cell whose analyzer writes version 23 needs a CLI that knows 23: an older CLI
refuses an analysis version it does not know, so with such a cell it refuses
every Route B patch until the CLI is upgraded. Ship the CLI first, then the
cell.

**Rollout.** The analyzer always writes `enclosingScope` (`{}` at minimum). A
document without it comes from a cell built before this change, and a class or
extension member cannot be shown safe without it, so such a target is refused
with "Re-cut the release". Every release already cut keeps the analyzer in its
cell, so patches to class and extension members on those releases are refused
until the release is re-cut with a current toolchain. Top-level functions are
unaffected.

### A patch may only name what the release kept (analysis version 18)

A replacement is compiled against the release's whole import kernel, so it
compiles any symbol it names. It runs against the release's AOT snapshot, and
the bytecode loader resolves every library, class, field and function by name and
aborts the process when one is missing (`bytecode_reader.cc`: `Unable to find
library`, `class`, `field`, `function`). Seam 6 attaches before `main`, so that
is a boot abort. Until analysis 18 nothing checked this: a dependency API the
release never called was refused by accident (the patched kernel shows its
closure as new classes), and a framework or SDK symbol the release never named
was not refused at all.

From analysis 18 the analyzer reports, for every member the patch would carry
(changed, carried, or a helper), the external symbols its body names:
`externalReferences`. The CLI then asks the release's own files, and refuses the
whole patch before anything is uploaded when a symbol is not shown to be kept:

| the symbol | kept when |
|---|---|
| public, in a library the interface lists whole (`library:` alone) | always |
| a member the interface names (`library:`, `class:`, `member:`): SDK members, framework and dependency members the release's own code named | the item is present |
| a class | a `class:` or `can-be-used-as-type:` item names it |
| a bare `class:` item (older generators) | the class and its public members |
| an instance member of a non-`dart:` class | the interface records the member (or its class item is bare, or its library is whole): an unnamed one loads but throws `NoSuchMethodError` when called, which is refused at patch time |
| private, and spelled by the patch | the capability manifest granted it (as for every private reference); a private class named as a type is also kept by an interface item for it |
| private constructor | not decided here: analysis 12's per-method release evidence decides whether a patch may construct it (the manifest withholds every construction, so asking it would refuse `createState() => _HomeState()`; the sweep arm found this) |
| private, and named only by a constant | the interface item for it is present |

**A patch that uses a widget or framework API the release never used is refused.**
That is the commonest consequence: after this lands, adding `Padding(...)`,
`Icon(...)`, `Theme.of(context)`, `EdgeInsets.all(8)` or `Navigator.of(context)
.push(...)` to a release whose own code never called them is refused, with the
symbol named and "cut a new release whose own code uses it". Evidence, from the
real loader (`probes/retention_loader.sh`, a dependency package standing in for
Flutter, one arm per kind of reference; Flutter itself was not run here):

| a body that names | loader | check |
|---|---|---|
| a class the release never used | aborts: `Unable to find class` | refused |
| a constructor, static, static field or top-level the release never named | aborts: `Unable to find function` / `field` | refused |
| a static or top-level the release reaches but never names (the AOT compiler inlined it) | aborts | refused |
| an instance member of a class the release kept, never named (field, getter, method) | loads; throws `NoSuchMethodError` when called (runs wrongly) | refused |
| a `dart:` instance member the release never called (`'abc'.toUpperCase()`) | loads; throws `NoSuchMethodError` when called | accepted: **known gap** |
| an extension getter, setter or tear-off (`Ext|get#x`) | aborts when the release lacks it | accepted only when the release's snapshot profile holds it with code, else refused |
| a local variable whose declared type is a class the release never used | loads | accepted |
| the same with `never-inline` on it | aborts | refused |
| a class the release allocates but never names, with a member it calls virtually (`(pick() as Circle).name()`) | binds | **refused anyway** |

The last row is the check's one measured conservatism, stated rather than hidden:
the snapshot has that class, but nothing at patch time says so (the interface is
the only witness), so it is refused as "never used in the release's own code". A
framework class that other framework code allocates (`Padding`, built inside
Material widgets) may be one of them. No static, top-level, constructor or field
arm bound without being named. Closing the class gap would take the release's AOT
kernel at patch time, which the CLI does not have; it is not done here.

The reason names the symbol, says the release never used it in its own code, and
says to cut a new release that uses it. Fail closed: no readable interface, a
body the analyzer could not walk, or a member the analysis recorded nothing for,
refuses.

What this does NOT check, so a pass is not read as more than it is:

- an instance member of a `dart:` class (`s.substring(1)`). **Known gap:** it
  binds by selector and the release generator leaves it out of the interface on
  purpose, so an SDK instance method the release never called can throw
  `NoSuchMethodError` on a device (measured: `sdk_instance_unnamed`). Refusing
  it would need the generator to retain SDK instance members, which costs
  every release code size (see `fw_use_binding.sh`'s `sdk-instance` arm);
- a reference the compiler adds that no source token names (interpolation,
  `for`, `async`), and `dart:_` libraries;
- an extension member (`list.firstOrNull`, `Ext|get#x`): no interface lists one
  (the generator skips `#` names), so the check asks the release's snapshot
  profile instead: it is kept when the profile holds a top-level function of
  that name, in that library, with code. A release that never called it (or
  marked it `vm:entry-point`, which also retains it) is the other case, and an
  unreadable profile refuses. This covers SDK extensions as well. An unnamed
  extension is named by its position in the library (`_extension#0|get#x`); a
  patch cannot add an extension, and the analysis refuses carrying one, so
  the position cannot shift under the name;
- the declared type of a local variable: measured to load without the class
  (`local_type_only`); an assignment or cast to it is a type node and is checked;
- that a kept symbol has code in the snapshot. Retention is not compilation (see
  `super0/s2b1e/`); this answers "can the loader find it", not "was it compiled".

The walker also reads type-parameter bounds and an async function's emitted value
type, as the release generator's collector does. It is the one piece of this that
needs the engine's `package:kernel`, so no CI job can run it; the CI tests cover
the matcher and the producer, and the host probes cover the walker, including an
invariant arm (`unchanged_release_sweep`): the release's own members, analyzed as
if carried against themselves, must all be kept.

Where it lives: the analyzer states the facts, because only it can read a kernel;
the CLI decides, because only it holds the release's interface and manifest
(`route_b_retention.dart`; the same split as private accesses, analysis 7, and
private constructions, analysis 12). The patcher asks before the coverage verdict
so a dependency API is named for what it is, and the producer asks again for the
members it carries (a carry can add members after the first analysis). A release
whose compiler cell predates analysis 18 cannot be checked: the patch is built as
before and the CLI says so at detail level, not as a warning (every older release
would print it on every patch, and nothing the developer can do changes it). This
takes effect for a release only once a cell with the version 18 analyzer is
minted and that release is cut on it. Host evidence: `probes/retention_check.sh`
and `probes/retention_loader.sh`.

Still refused, before anything is uploaded, with the reason named:

- a **public** new instance method (outside code can call it by name, for example
  `jsonEncode` calls `toJson`; run as edit r1, exit 70);
- a new private name that another member of its library already uses, even in
  another class (run as edit r2, exit 70);
- a new top-level function that something outside the patch also calls, a new
  class, a new field, and the other shapes listed as refused in `PARITY.md`.

The cell `aab9fd07` and earlier refuse every new member. Not exercised on a
device: a patch whose added method is reached only by a tap, a new method on a
class other than `State`, and an obfuscated release.

The text below was written before D-SUPER-2C and describes the rule; its
"no release" applies today only to the published 3.47 cell.

**No published release can use this today.** The producer carries a zero-argument
`super.foo()` only when the resolved compiler cell implements
`routeBDirectSuperDualKernelV1`, and no published cell does — so every shipped
release still refuses, exactly as the row above says. What follows describes
certified host behaviour, not a user-visible capability.

The rule, and every clause of it is a measured boundary rather than a
preference:

> A zero-source-argument `super.foo()` is carried only when the RELEASE version
> of the same method already direct-called a target with the same semantic
> provenance.

    analyzer (patched AOT)   the site exists, and the target it authorizes
    patch source             what the developer wrote — argument presence
    patched no-AOT kernel    the compiler's own verification of both
    release import kernel    what the emitted bytecode binds against

Three provenance fingerprints — analyzer, patched verifier, release binder —
must agree, and the emitted `DirectCall` names the RELEASE procedure.

Why each authority is where it is:

* the AOT kernel cannot answer what was written: TFA rewrites
  `super.tag('a', 7)` to zero arguments there (`super0/s2b0/`);
* a call SITE offset is not a cross-version identity, and using one as such
  produced silent wrong semantics on a byte-aligned specimen
  (`super0/s2b1site/`);
* a target's canonical owner is renamed by AOT mixin deduplication, so only
  `fileUri | fileOffset | name | kind` crosses the boundary (`super0/s2a/`);
* retention is not compilation: a mixin-application clone can be retained by
  name with no AOT code, and a `DirectCall` to it aborts the app at
  `compiler.cc:1152` (`super0/s2b1e/`). The same-method evidence rule is what
  keeps that unreachable.

Still refused, and unexercised: arguments, getters, setters, generics. Since
Dart lineage PR #5 the compiler also refuses a target that is not a concrete
method in either kernel, and requires the entry point's receiver class to be
the origin class (a `dynamic` receiver is cast to it at run time).

#### The boundary, stated once

> **If one source token requires more than one semantic receiver operation,
> refuse it.**

That is what the "two accesses at one offset" check enforces. It is a product
boundary, not an implementation limit, and it should be defended rather than
chipped at.

`slot += f()` is not `self.slot = self.slot + f()` unless you have proven
evaluation order, the number of getter and setter invocations, operator
dispatch, and the value the expression yields. `slot++` and `++slot` differ in
result. `slot ??= f()` must short-circuit both the right-hand side *and* the
write. Overloaded operators complicate the read/operate/write sequence again.
None of that is transport; all of it is reconstruction.

So if compound writes are ever needed, they are **a new lowering subsystem with
explicit semantics per Kernel shape** — not another case in the lexical editor.
`super` is separately different: there is no textual equivalent once the method
becomes a synthetic top-level function, and `self.foo()` would re-dispatch into
the override. It needs the Kernel-resolved superclass target driving a
representation the payload does not currently have.

**Let real patch demand decide which earns a design.** The surface above is
already broad enough to run Route B against representative real-world patches,
and what those block on is better evidence than what a ladder suggests next.

> One loose end, deliberately not spent on: the analyzer's refusal text for a
> compound write still reads *"cannot rewrite as a single edit"*, which sounds
> like a limitation rather than a boundary. Rewording it changes the cell and so
> costs a mint; fold it into the next mint that happens for another reason.

- The generator's source has moved while the pinned

## What you are building, in one shape change

Route B is **not** building a Dart interpreter. Vanilla Dart 3.12.2 already
contains everything that would have meant reproducing Shorebird's private fork,
behind the `dart_dynamic_modules` GN flag: bytecode execution, `InterpretCall`,
`Function::AttachBytecode`, and the runtime ability to redirect a `Function`
into interpreted bytecode.

Route B is the **binding and dispatch layer** that lets a normal AOT Shorebird
app opt *specific* calls into that machinery. Today an AOT call says:

```
call this compiled machine-code target
```

A patchable call has to say:

```
call this Dart Function object, through its current entry point
```

Normally that entry point *is* the AOT implementation, so nothing changes and
nothing is slower except the call sequence itself. After a patch:

```
AttachBytecode(Function X, newBytecode)
  -> Function X now enters the interpreter
  -> existing callers start running patched Dart
```

No rewriting of executable pages. No new VM. No second runtime. That is the
whole idea; everything below is making it safe, general, packageable,
measurable, and compatible with the existing updater lifecycle.

## The first success criterion — keep it almost stupidly small

Do not aim at "arbitrary Dart patches anywhere". Aim at this:

> A real release on an iPhone contains **one** patchable Dart function.
> `shorebird patch` changes that function. The existing updater receives the
> patch. `AttachBytecode` activates it. **The UI visibly changes.** Rollback
> restores the original AOT behavior.

When that loop survives release → patch → rollback, Route B is real. Widening
the supported surface comes after, deliberately, from an inventory of call
forms — not before.

**One premise in that reasoning was wrong, and it mattered.** The note that
`FUNCTION_REG` "on arm64 is carrying an argument" is not true at a static call
site: `R0` is the call's *output* register, a static call's `LocationSummary` is
`kCall` so every volatile register is already clobbered, and Dart arguments are
passed on the stack. `R0` was free the whole time. Step 1 writes the `Function`
into it and the callee never notices. If you are re-deriving this, check the
register's actual liveness rather than inheriting the claim.

## What "patchable" now covers — measured 2026-08-09

The narrow definition was *static Dart calls, explicitly compiled in Route-B
patchable mode*, with widening deferred until an inventory existed. The
inventory exists — `engine/route_b/inventory/` — and it is one program
exercising each shape AOT actually emits:

| form | patchable |
|---|---|
| top-level static, static method | **yes** |
| instance method (monomorphic), getter | **yes** — AOT devirtualizes these into static calls |
| dynamic instance call (`EmitTestAndCall` cid chain) | **yes** |
| statically-typed polymorphic call (**dispatch table**) | **no** — **yes** under `--route_b_untabled_overrides` (2026-11-14, host; 2026-11-15, an iPhone from a local cell; 2026-11-16, an iPhone through the published cell `aab9fd07`, and again through `2fc41d3f`) |

Dispatch-table calls load a raw entry point out of a data table and set up
neither `R0` nor `R4`, so there is no cheap version: rewriting the table is
legal on iOS but insufficient, and making `EmitDispatchTableCall` go through the
`Function` taxes **every instance call in the program** — straight onto the step
7 veto. That decision wants the real-app benchmark first.

**2026-11-14: a targeted version instead.** `--route_b_untabled_overrides`
(Dart lineage PR 3) keeps a selector out of the table when a regular method
implementing it lives outside `dart:` and `package:flutter/`, so its calls stay
switchable calls (or cid-check chains), whose stubs load `R0` and `R4`. Every
`Widget.build` an app defines is such a selector. The cost is not confined to
the app: a selector is shared by every class that implements it, so an app
`build` untables the framework's `build` calls too, and an app class
implementing `Iterable` or `Map` would untable those SDK calls. Pub packages
count as app code here. On a counter app
the snapshot grows 0.33 %, the call-form inventory reports the polymorphic and
megamorphic forms patchable, and the release probe (revision 2) finds call sites
for `MyApp.build` and `_MyHomePageState.build`. Measured on the host only, on
one small app. The device patch and the size on a second small app followed
on 2026-11-15 (below). A published iOS cell, and size and frame time on a real
app, are still to come. See
[`engine/route_b/evidence/untabled_overrides/RESULT.md`](engine/route_b/evidence/untabled_overrides/RESULT.md).

**2026-11-15: on an iPhone, from a local cell.** A patch to one override of a
polymorphic method (`Circle.describe`, with `Square.describe` left alone) ran on
an iPhone 7. It was one of 16 targets in one patch to a small Flutter app. Two
Dart changes were needed first (lineage PR #6):
- a patch calling an SDK member AOT had removed (`List.add`, `join`) needed the
  loader to supply a stand-in and the SDK member to be findable by name;
- the interpreter passes every argument on the stack, so selectors with such a
  member now use the stack calling convention everywhere. Without that, a
  patched `for`-in over a `List` crashed.

Snapshot size on that app: +1.01 % with SDK name lookup on. Frame time was not
measured. See
[`engine/route_b/evidence/ios_shapes_2026_11_15/RESULT.md`](engine/route_b/evidence/ios_shapes_2026_11_15/RESULT.md).

## Traps that will bite you

These are not hypotheticals; each one cost real time.

1. **The killgate rig and the iOS-engine rig cannot share one Dart checkout.**
   *(Already acted on — `/Volumes/build/route-b` exists. Kept so nobody
   "consolidates" the two trees later to save disk they are not actually
   spending: the clone is copy-on-write.)*
   `engine/killgate/0001-attach-bytecode-native.patch` modifies
   `sdk/lib/_internal/vm/lib/internal_patch.dart` and `sdk/lib/internal/internal.dart`
   — **SDK sources**, which compile into `platform_strong.dill` regardless of
   the GN flag. Mixing them into an iOS engine build fails the AOT step with
   `Unexpected tag 4 (Field)`, which names nothing useful. Route B needs
   `dart_dynamic_modules = true` *and* those edits, so **give it its own
   checkout** and run `dart_patches.sh --verify` on both.

2. **Experimental instrumentation does not stay in the production tree.** Spike
   A's `--dump_global_object_pool_to` sat in the shared Dart source and made
   every out-dir built from that tree carry it. Reverted 2026-08-07. Keep the
   patch file, not the working-tree edit.

3. **`gclient sync` replaces the Dart tree with what DEPS pins.** `managed: False`
   protects the flutter checkout's git state, not the DEPS-managed subtrees.
   Our Dart changes are commits on the Dart fork
   and `dart_patches.sh --apply` is retired; recovery is to sync to the fork
   commit the tree's own DEPS pins (`main`: `b4671ab7`; the 3.50 candidate on
   `selfhost/dart-3.14`: `0cd04a77`). Run `--verify` after *any* sync,
   before wasting a build.

4. **The engine hash is sha1 of the Flutter binary only.** A `gen_snapshot`-only
   change republishes under the *same* hash — delete `bin/cache/engine.stamp`,
   `engine_stamp.stamp` and `bin/cache/artifacts/engine/ios-release` or the
   build silently reuses the old compiler.

5. **Snapshot and kernel formats are welded to the tree that produced them.**
   The whole host toolchain must share one tree *and* one GN config:
   `frontend_server_aot` → kernel → `gen_snapshot` → snapshot, against the
   platform dill. A mixed set installs fine and dies at launch with
   `Wrong full snapshot version`.

6. **"It built" proves nothing about a fork/backend pairing.** A mismatched
   frontend/backend compiles cleanly and only fails on the device, which is why
   `dart_sdk_compatibility.dart` is an identity check rather than a probe.

7. **A fast loop exists — use it.** No Xcode, no device, no server:
   `gen_snapshot --deterministic --snapshot_kind=app-aot-assembly
   --assembly=/tmp/out.S app.dill` reproduces a compiler crash in 0.24 s, and
   `ninja -C out/host_debug_arm64 -j8 gen_snapshot` rebuilds in ~80 s. The
   debug host build prints a full stack and the crashing function's CFG.

8. **`ASSERT` is compiled out** in `gen_snapshot` (`-DNDEBUG`) *and* in the
   `host_debug_arm64` build (`dart_runtime_mode=develop`). A VM invariant you
   are relying on may be silently violated. Turn the relevant `ASSERT` into
   `OS::PrintErr` + `Profiler::DumpStackTrace(false)` rather than trusting it.

## What not to do

- **Do not start Track C (hot restart).** It adds a second runtime lifecycle
  axis before Route B's activation/rollback model exists. It layers on top of
  Route B, not beside it.
- **Do not chase the TFA root cause** as a prerequisite. It is a real
  compiler-correctness project ([`TFA_ROOT_CAUSE.md`](TFA_ROOT_CAUSE.md)) and
  the four compensating patches are device-verified. Deleting them is a
  cleanup, not a blocker.
- **Do not reopen the infrastructure track.** Artifact ownership, the mirror,
  the fixture and the rig state are closed and guarded. If a guard fires, it is
  telling you something true.
- **Do not widen the sealed-run claim to "no network."** The criterion is
  *nothing closed is required*. GitHub, pub.dev and Apple's signing
  infrastructure are all permitted; none of them serves a Shorebird artifact.
- **Do not build a second interpreter.** The one in vanilla Dart is the one.
- **Do not try to make every AOT call patchable immediately.** See the design
  decision above; breadth before the first working loop is how this explodes.
- **Do not invent writable-executable-page patching on iOS.** It is illegal
  there, and it is the reason the pool-rewrite and unlinked-call routes were
  ruled out.
- **Do not pursue Route A / object-pool relinking.** That decision is made.
- **Do not change the infrastructure or mirror architecture.** Closed and
  guarded; a firing guard is telling you something true.
