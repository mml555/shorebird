### No row in #69's territory can reach whole-row PROVEN

`rows_whole_row_promotable` computes to `[]`.

Every one of the 13 rows declares `jit` cells, and Mutable-AOT has no
JIT mechanism. This is mechanical, not a schedule:

* the dispatch-cell lowering exists **only** in
  `flow_graph_compiler_arm64.cc` — 11 references there, 0 in
  `flow_graph_compiler_{arm,ia32,riscv,x64}.cc`;
* it is gated on `FLAG_precompiled_mode`
  (`flow_graph_compiler_arm64.cc:423`), so it never fires in JIT.

A `jit` cell is therefore unreachable **by construction**, not merely
undone. Exactly half the declared cells (88/176) are in that state.

This is what the EB-03 amendment protects against: #69's maximum honest
reach is 62/176 = 35% of the cells those rows declare. A blanket
"relevant rows become PROVEN" would have promoted 13 rows, and 28 cells
of EB-03 alone, on roughly a third of their evidence.

### One scoping interpretation, flagged

`dynamic` is treated as #69's megamorphic/switchable-call case. The issue
says "megamorphic/interface calls where applicable" and never writes
`dynamic`, so this is an interpretation — but EB-03 declares `dynamic` as a
mode distinct from `interface`, so covering EB-03 at all requires owning it.

### A specification question this exposes

If a row can never be `PROVEN` while it declares `jit` cells, then row-level
`PROVEN` is unreachable for all 13 rows permanently, not just until #70. That
is a program-level question and I am not deciding it. The options appear to
be: aggregate closure needs a JIT mechanism; or the row model needs an
"AOT-complete" result distinct from `PROVEN`; or those `jit` cells should be
re-declared out of scope. #69 proceeds correctly either way, because it
claims cells and not rows.

## 2. Dispatch architecture inventory

What each structure actually holds, read from the fork at
`b92efd823d83`. The answers differ per structure, so a single mechanism
cannot be assumed.

| structure | what it resolves to | observes a cell install? |
|---|---|---|
| AOT dispatch table | **raw entry-point address** in a `uword[]`, `Call [DISPATCH_TABLE_REG + (cid + selector_offset)*8]` | **no** |
| `MegamorphicCache` | a `Function` (`kTargetFunctionIndex`) | possibly — has a hook |
| `super.foo()` | lowered by `BuildSuperMethodInvocation` → `BuildStaticInvocation` | **likely already yes**, via #67 |
| tear-off | a *distinct* `Function` from `ImplicitClosureFunction()` | no — separate identity |
| `SingleTargetCache`, `UnlinkedCall`, `MonomorphicSmiableCall`, `ICData` | not yet inventoried | unknown |

### The dispatch table is the hard case

`dispatch_table_generator.cc:258`:

```cpp
code_ = function->CurrentCode();
entries.SetAt(selector()->offset + cid, code_);
```

The slot is resolved from `function->CurrentCode()` at snapshot time and
called as a raw indirect branch. Nothing about it consults a `Function`, a
`Code` object, or a #66 dispatch cell — which is exactly the Route-B
divergence this issue names: direct → NEW while virtual → OLD.

### Candidate mechanisms

1. **Slot holds a cell-dispatching stub.** One extra indirection, paid only
   by mutable declarations' slots. The table then stays valid forever — the
   "resolves through a mutable slot" branch of the cache requirement, with
   no invalidation to get wrong.
2. **Rewrite table entries on install.** The table is a heap `uword[]` and
   is writable, but this needs a serialized reverse index from declaration
   to every `(selector, cid)` slot, and one inherited `Code` appears at many
   cids.
3. **Make `CurrentCode()` itself the trampoline for mutable declarations,
   before table generation.** Then (1) falls out everywhere at once —
   dispatch table, megamorphic cache, tear-offs — because every structure
   that resolves a mutable declaration to code at snapshot time picks up the
   indirection. This is the issue's "class method entry itself becomes a
   mutable descriptor-backed target".

(3) looks strongest and is checked first. It must not disturb #66's
constraint that two `Code` objects with identical `Instructions` cannot both
be reachable after `ProgramVisitor::Dedup`; a per-declaration trampoline
embeds its own cell, so its instructions are distinct.

Nothing here is a decision yet. The next checkpoint completes the inventory
for the four uninventoried caches and states, per structure, whether it stays
valid via the slot or must be invalidated — with the runtime decision that
consumes each invalidation named.

## Not claimed

* `super` being a static call is read from the lowering, not measured. It

* The four uninventoried caches may each change the picture.
