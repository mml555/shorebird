## The `_CustomFocusBuilder` control — why, exactly

`AppBtn.build` is analyzer-ADMISSIBLE: `unsupported` empty, no super site. The
producer refuses it. Against the release's OWN manifest, not a synthetic grant.

The release's manifest says why:

    privateClassesConstructible          0
    constructionWithheld               119
      …/buttons.dart#_CustomFocusBuilder.new        WITHHELD
      …/buttons.dart#_CustomFocusBuilderState.new   WITHHELD
    privateClassPublicMembers          414
      …#_CustomFocusBuilder#createState             granted
      …#_CustomFocusBuilder#builder                 granted

and the body constructs it — `buttons.dart:144`, `Widget button =
_CustomFocusBuilder(`.

So under policy p2 a private class is retained **so its members can be
patch-targeted**, while its CONSTRUCTION is withheld separately. A replacement
declaration for `AppBtn.build` is recompiled whole and would construct
`_CustomFocusBuilder`; the release never retained that constructor, so the patch
would fail to bind on the device.

**The producer is right, and it was not loosened.** The analyzer was missing a
fact it can measure soundly.

## The parity fix — implemented and validated

`analysisVersion` 12 adds `privateConstructions` to each method's lowering: every
construction of a private class in the body, carrying the manifest key the
release would have had to grant.

    "privateConstructions": [
      { "offset": 4631,
        "library": "package:wonders/ui/common/controls/buttons.dart",
        "class": "_CustomFocusBuilder", "constructor": "new",
        "key": "package:wonders/ui/common/controls/buttons.dart#_CustomFocusBuilder.new" }
    ]

Validated against the real release manifest — all three keys the body needs are
reported, and all three are ones the release withheld:

    _CustomFocusBuilder.new    WITHHELD (patch would refuse)
    _ButtonPressEffect.new     WITHHELD (patch would refuse)
    _ButtonHoverEffect.new     WITHHELD (patch would refuse)

Two design points:

* **REPORTED, never refused here.** Same division of labour version 7
  established for private member accesses: the manifest is a per-release
  artifact and the analyzer ships in a cell resolved by engine hash, so it
  states the fact and the holder of the manifest decides. The answer genuinely
  depends on the manifest — p2 withholds construction while granting members —
  and cannot be decided in the analyzer.
* **Scoped to the method's OWN library.** Dart privacy is library-scoped, so a
  private class named in a body can only be declared there, and that is exactly
  what the producer's source scan can see. Without the filter the list fills
  with SDK internals the compiler synthesised (`dart:core#_GrowableList._literal1`
  from a list literal): never named in source, not the app's to grant, and not
  something the producer refuses on.

### The fix is NOT landed, and needs a decision

`supportedRouteBAnalysisVersion` is an EXACT-match gate. Shipping v12 requires
the CLI to move to 12 **and** a new compiler cell carrying the v12 analyzer,
mapped and activated. Every published cell — including certified H3 — ships v11,
so bumping the CLI alone would break patching against every existing cell. The
analyzer source change is committed; the CLI bump and the cell mint are not, and
should not be done without authorisation.

## Pre-existing blockers by fix type

D-DEMAND-1 measured that essentially every blocker is PRE-EXISTING: the
developer did not touch it. Classified as the ruling asks:

| blocker | count | class | why |
| --- | --: | --- | --- |
| private type construction | 7 | **B** | The construct is unchanged and the class IS retained — only its constructor is withheld, by policy, so that members stay patch-targetable. Widening p2 to retain private constructors, or binding the patch to the released constructor, would carry it without implementing any new Dart. |
| capability not granted | 2 | **B** | Same shape: a private member the release did not retain. A retention decision, not a language feature. |
| method tear-off | 9 | **A** | The lowered spelling is the same textual edit as a read (`self._handleTap`), but the replacement compiler must be able to emit an instance tear-off. That is a feature. |
| named / optional parameters | 7 | **A** | The replacement is a top-level function whose signature must express the original's ABI; the bytecode compiler cannot currently declare these shapes. |
| compound same-offset read+write | 2 | **A** | One identifier doing two jobs at one offset; the lowering cannot express it as a single edit. |
| receiver rewrite | 1 | **A** | The producer cannot rewrite that particular receiver access safely. |
| unreachable | 2 | — | Not a blocker to fix: the release genuinely cannot reach the member. |

**C is empty on this evidence.** Nothing in the observed refusals is caused
purely by the replacement unit being a whole method: every one is either a
retention/evidence decision (B) or a capability the replacement compiler lacks
(A). So this measurement does **not** support opening a sub-method architecture
project — which is the question the ruling wanted answered before that could be
discussed.

The B group is 9 of 28 producer refusals (32%) and is the larger single lever
per unit of work, because it needs no new Dart support at all.

## Corrections to D-DEMAND-1's banked numbers

**LocalSend's corpus included generated code.** The precommit excludes generated
files by the declaration-marker rule, and `demand_report` applied that filter to
census rows but not to the observations built from pair documents — so 21
slang-generated methods were counted. A corpus that is 97% codegen must not
re-enter through that door. Corrected:

    LocalSend changed methods   253 -> 232
    LocalSend admissible        233 -> 220
    LocalSend compatibility   92.09% -> 94.83%

Wonderous is unaffected (0 generated). Also reported now: 26 LocalSend
observations are not present in their candidate census, which is visible in the
row rather than silently absorbed.

**A harness defect that inflated producer refusals.** The producer reads a
body's source from `span.fileUri`, which points into the harness worktree.
Building the release's manifest left that tree at the BASE commit, so the first
replay pass read the RELEASE's text against the CANDIDATE's spans and produced
refusals like "its recorded source span runs past the end of …" and "its
parameter list could not be found" that described the harness. The tree is now
checked out to the CANDIDATE before every replay. The correction moved both
numbers, in opposite directions — Wonderous 50.00% -> 45.00%, LocalSend
85.38% -> 86.96% (then 92.67% after the generated-code fix) — which is why it
could not be dismissed as a one-way artifact.
