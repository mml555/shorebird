############ 4. private-reference identity must be EXACT ############
   Corpus corpus_ext/g5_accessor_pair declares a private GETTER and a
   private SETTER both named _x, so a reference resolved only to
   (library, owner, name) cannot say which declaration it meant.

   as built -- each reference carries the kind read off the resolved Member:
      Holder.readIt   read   -> Holder#getter#_x
      Holder.writeIt  write  -> Holder#setter#_x
    Holder.readIt   -> ['MISSING_CAN_BE_OVERRIDDEN', 'RETENTION_UNPROVEN']
    Holder.writeIt  -> ['MISSING_CAN_BE_OVERRIDDEN', 'RETENTION_UNPROVEN']

   4a. REMOVE the recorded kind from every reference
    Holder.readIt   -> ['MISSING_CAN_BE_OVERRIDDEN', 'PRIVATE_REFERENCE_UNRESOLVED', 'RETENTION_UNPROVEN']
    Holder.writeIt  -> ['MISSING_CAN_BE_OVERRIDDEN', 'PRIVATE_REFERENCE_UNRESOLVED', 'RETENTION_UNPROVEN']

   4b. CORRUPT the kind: the setter's write now points at the getter's row
    Holder.readIt   -> ['MISSING_CAN_BE_OVERRIDDEN', 'RETENTION_UNPROVEN']
    Holder.writeIt  -> ['MISSING_CAN_BE_OVERRIDDEN', 'PRIVATE_REFERENCE_UNGRANTED', 'RETENTION_UNPROVEN']
      -> the getter row has no write key, so it refuses. A wrong row still
         fails closed; it does not quietly authorise the write.

   4c. WHICH G3 ROW EACH STRATEGY SELECTS
   The first version of this arm claimed the reinstated fallback would silently
   resolve; its own output refused instead, because the stale-input guard runs
   before the fallback. Rather than leave a caption the evidence contradicts, the
   arm is replaced with the direct comparison it was trying to make: for the same
   reference, which G3 row does each lookup strategy pick?

      Holder.readIt   read   exact-> getter  (write_key=False)   fallback-> getter  (write_key=False)
      Holder.writeIt  write  exact-> setter  (write_key=True)   fallback-> getter  (write_key=False)

      The fallback searches field -> method -> getter -> setter and stops at the
      first hit, so BOTH the read and the write select the GETTER row. The write
      would then be judged against a declaration that has no write key at all --
      a different declaration from the one the body actually names. On this
      corpus that happens to be less permissive, so the harm here is a wrong
      attribution rather than an over-claim; the exact lookup removes the class
      of error rather than relying on it landing safely.

   restored:
    Holder.readIt   -> ['MISSING_CAN_BE_OVERRIDDEN', 'RETENTION_UNPROVEN']
    Holder.writeIt  -> ['MISSING_CAN_BE_OVERRIDDEN', 'RETENTION_UNPROVEN']

############ 5. an ALLOWLISTED node with no fact-bearing visitor ############

   that carry a member reference with no visitor. "Allowlisted" was being used
   to mean "understood", and it was not: a private reference through such a node

   An audit of every allowlisted kind for Reference/Name/Member fields split
   them into modelled, removed, and genuinely referenceless. corpus_ext/
   g5_tearoff reaches a private member through four of the previously unmodelled
   shapes.

   as built --
      viaStaticTearOff     supported                  ['#method#_secret']
      viaSuper             supported                  ['Base#method#_hidden']
      viaInstanceTearOff   supported                  ['Base#method#_hidden']
      viaDynamic           refused:DynamicInvocation  []

   5a. DELETE visitInstanceTearOff, leaving InstanceTearOff allowlisted
      viaInstanceTearOff   supported                  []
      -> the private tear-off becomes INVISIBLE: status still "supported", no
         reference recorded. This is the defect exactly.

   5b. RE-ALLOWLIST the dynamic nodes, which carry a Name but no resolved target
      viaDynamic           supported                  []
      -> flips from refused to "supported" with nothing recorded. An unresolved
         dynamic private access must never become "no private reference found",
         which is why those kinds are removed rather than modelled: there is no
         exact identity to record.

   5c. A CORRECTION TO THIS ARM'S FIRST VERSION, kept rather than quietly fixed.
   It deleted visitStaticTearOff alone and claimed the static tear-off would go
   invisible. Its own output showed the reference still present, because in this
   kernel the tear-off is ALSO carried as a StaticTearOffConstant, which the
   constant walk records. Deleting both paths gives:

      viaStaticTearOff     refused:Constant:StaticTearOffConstant  []

   -- it REFUSES rather than going silent, because the constant walk's default
   branch is fail-closed. So the static tear-off is covered twice over, and the
   arm that actually demonstrates the false negative is 5a.

   restored:

      viaSuper             supported                  ['Base#method#_hidden']
      viaInstanceTearOff   supported                  ['Base#method#_hidden']
      viaDynamic           refused:DynamicInvocation  []
