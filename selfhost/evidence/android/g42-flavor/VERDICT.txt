B4 — SAME FLAVOR, RELEASE -> PATCH -> DEVICE.  **PROVEN.**
  release --flavor foo (2.0.0+1)   FLAVORPROBE-V1   flavor: foo
  patch   --flavor foo (patch 1)   FLAVORPROBE-V2   flavor: foo
Two independent readings on purpose: the MARKER proves patched code executed,
the FLAVOR proves the configuration survived. The APK came from the REGISTERED
release artifact downloaded from the control plane, not from the local build
tree — `shorebird patch android` re-runs `flutter build appbundle` and
overwrites it, which is the trap G10.2 recorded hours earlier.

Note for iOS readers: `flavor: foo` is LOWERCASE here. Android takes the CLI
token; only darwin takes the Xcode-configuration route (common.dart), which is
why iOS shows `Foo`. Same fixture shape, different value, by design.

So on Android a wrong-flavor patch is not fingerprinted, not refused, and runs.
It changes the app's own flavor identity at runtime. This is consistent with the
source: `grep -c RouteBBuildConfig android_patcher.dart` -> 0, and
RouteBBuildConfig appears only in iOS/Route B files. Configuration comparison is
an iOS/Route B mechanism; the Android path has none.

WHY THE TWO-APP_ID REFUSAL MUST NOT BE BANKED AS THE ARM PASSING: it is a
refusal for the wrong reason, and the plan warned about exactly this shape —
"a wrong-reason refusal in the mismatch arm reads exactly like the right one."
Only the one-app_id control distinguishes them, which is why it was run.
