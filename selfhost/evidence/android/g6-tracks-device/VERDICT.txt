THE SETUP, and why its ORDER is the whole experiment
----------------------------------------------------
  patch 1  ->  track `stable`   marker TRACKPROBE-STABLE
  patch 2  ->  track `beta`     marker TRACKPROBE-BETA     PUBLISHED SECOND

Beta's patch is the NEWER one. That is deliberate. A device asking for `stable`
must receive patch 1; if track selection were not real -- if the server or the
updater simply served the newest patch -- it would receive patch 2. So "asked
stable, got STABLE" is a DISCRIMINATION and not a tautology.

Publishing beta's patch first would have made the arm unfalsifiable: asking
stable and getting stable's patch would then be consistent with both "tracks
work" and "latest wins". This is the same failure the G4.2 lane hit when a
two-app_id shorebird.yaml produced a right-looking refusal for the wrong reason.

SERVER PRECONDITION (checked before touching the device, so a vacuous arm
would have been caught early):

  POST /api/v1/patches/check  channel=stable  ->  patch 1
  POST /api/v1/patches/check  channel=beta    ->  patch 2

THE DEVICE ARM
--------------
  1  launch                    TRACKPROBE-V1      current none  next none
  2  check(stable)             UpdateStatus.outdated
  3  update(stable)            current none  next 1        (staged, not active)
  4  restart                   TRACKPROBE-STABLE  current 1  next 1   <== DECISIVE
  5  check(beta)               UpdateStatus.outdated
  6  update(beta)              current 1     next 2        (both tracks at once)
  7  restart                   TRACKPROBE-BETA    current 2  next 2
  8  check(stable) on beta     UpdateStatus.upToDate       (see the nuance below)

WHAT EACH STEP IS FOR, because several are easy to over-read
------------------------------------------------------------
* STEP 1 is not decoration. BOTH patches already existed on the server, and
  neither applied. That is `auto_update: false` doing its job, and it is a
  precondition for everything after: if the runtime could apply a patch on its
  own, the device could acquire BETA's patch without any Dart call having asked
  for beta, and the entire track reading would collapse.

* STEP 4 IS THE CLAIM. Not "a patch arrived" -- WHICH patch arrived. The marker
  is compiled Dart, so TRACKPROBE-STABLE can only have come from patch 1's code
  actually executing. The patch NUMBER alone would not have distinguished the
  tracks nearly as well, and the marker and the number agree.

* STEP 6 shows current 1 / next 2 SIMULTANEOUSLY -- the stable patch running
  while the beta patch is staged. One screen, both tracks, same install.

* STEP 8 IS NOT A SUCCESS AND IS NOT A FAILURE. Read it carefully. The device
  is on patch 2 (beta's) and asks stable, whose patch is 1. It answers
  upToDate -- it does NOT offer to move the device back to stable's patch.
  The check compares patch NUMBERS, and patch numbers are global per release
  rather than per track, so a device that has consumed a higher-numbered patch
  from another track reads as up-to-date against a lower-numbered track.

  So the row's claim holds for ACQUISITION -- a device gets only the track it
  asks for -- but "membership" is forward-only by patch number. Asking for
  stable does not return a beta device to stable's code. Whether that is
  desirable (no silent downgrades) or a gap (no way back) is a DECISION, not a
  test result, and it is recorded here rather than resolved.
