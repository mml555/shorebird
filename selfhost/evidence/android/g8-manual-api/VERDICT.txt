WHAT EACH LINE IS FOR, because three of them are easy to over-read:

* TWO launches before touching anything. Patch 1 already existed on the server.
  With `auto_update: false` nothing applied across either launch — that is the
  fixture's actual claim: no update happens behind the app's back. One launch
  would not have shown it.

* `update()` leaves current=none and next=1. Staged, not active. That separates
  readNextPatch from readCurrentPatch on real hardware rather than by reading
  the header docs.

* THE NUMBER ALONE WOULD PROVE NOTHING. Precommitted outcome 9 names this as an
  easy false green: readCurrentPatch is ALREADY exercised by every airgap
  release, so a patch number on screen is not evidence for checkForUpdate or
  update(). Two independent guards were built in:
      - the fixture captures the value BEFORE update() and displays it
        (`before update(): none`), so the claim is that the number CHANGED
        across a call we made;
      - the MARKER (V1 -> V2) is compiled Dart, so patched CODE demonstrably ran.
  Either alone is weak; together they exclude the false green.

* checkForUpdate returned `outdated` BEFORE update() was pressed, which is
  precommitted outcome 8's condition. Outcome 8 grants BUILT for that on host
  and PROVEN only once the update installs and the patched value renders — both
  of which are above.
