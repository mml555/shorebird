# Classification contract — precommitted before touching the 1,735

Written 2026-08-16, **before any finding is reclassified**, because the step that
lowers the count is also the step that decides what the restored gate can never
see again. Policy invented while watching a number fall is policy fitted to the
number.

## Two corrections to the earlier framing, both measured

The `evidence/cspell/README.md` categories said roughly *"categories 1–2 (~60 %)
are generated artifacts and vendored C++ identifiers inside `.patch` files —
`ignorePaths`, not words."* **Both halves were wrong**, and the second was
dangerous.

| | claimed | measured |
|---|---|---|
| exclusion can absorb | ~60 % | **508 / 1,770 = 29 %** |
| `.patch` handling | blanket path exclusion | **impossible without blinding authored prose** |

`.patch` files carry **4 findings in headers this repository writes** against 174
in diff bodies. Small in count, and they are the highest-value prose in those
files — patch headers are where obligations like *"the negative control is OWED"*
live. A blanket `**/*.patch` exclusion would have removed them silently, which is
precisely the easy-and-dangerous move to avoid.

The real shape of the debt:

| class | findings | disposition |
|---|---|---|
| generated / captured artifacts | 508 | exclusion candidates (§1) |
| `.patch` diff bodies | ~136 | line-scoped override, **not** path exclusion (§4) |
| authored prose + scripts | 1,122 | dictionary / normalization / review (§2, §3) |
| — of which accepted spelling variants | 237 | mechanical (§3) |

So exclusion is the *minority* of this work, and the bulk is authored content that
must stay visible. That inverts the earlier plan's centre of gravity.

## The ordering principle: prefer the smaller blind spot

> **Where two categories can both resolve a finding, the NARROWER one wins.
> §4 (line-scoped) beats §1 (path-scoped); §2 (dictionary) beats §1.**

A path exclusion is the largest instrument available and it is permanent by
default: nothing inside it is ever looked at again, and no future finding will
announce that the boundary got too wide. A narrower rule that costs some
configuration complexity buys back everything the wide one would have silently
covered.

**Promoting a whole path class to `ignorePaths` needs an invariant, not an
observation.** *"There is currently no authored prose in these files"* describes
today's generation shape; it is not a property the format enforces. The bar is
something like: **the files are regenerated from another canonical artifact, and
modification outside the generator is mechanically rejected.** Absent that, use
the line-scoped rule and let a future header, trailer, generation note or
obligation stay observable automatically.

## The four categories, with admission tests

A finding is moved only if it passes the test for exactly one category, and by
the narrowest category that fits. **The default is §5: stay visible.**

### §1 — Ignore path/pattern

**Admission test, all three required:**

1. the content is **generated, captured, or vendored** — produced by a tool, a
   device, or upstream, not authored here;
2. **no human edits it in this repo**, so no misspelling it contains could be a
   mistake anyone here can make or fix;
3. it carries **no prose** — no comment, header, or narrative a reader would rely
   on.

**Proposed exclusions, each with the counterexample that would make it too
broad:**

| path | why it cannot carry spelling signal | counterexample that falsifies the exclusion |
|---|---|---|
| `selfhost/evidence/releases/*/obfuscation_map.json` (348) | `gen_snapshot` output; identifier→identifier mapping, machine-written and machine-read | anyone ever hand-edits one, or a reviewer reads one as documentation |
| `selfhost/engine/route_b/instrumentation/*.snapshot` (68) | verbatim copies of upstream C++ kept for diffing; edits belong in the source tree, not here | a snapshot acquires a locally written header explaining what it captures |
| `selfhost/evidence/**/*.trace` (54) | device trace output, captured verbatim | traces start carrying an authored annotation block |

**Withdrawn from this table 2026-08-16:
`selfhost/engine/route_b/instrumentation/*.fulldiff.patch` (38).** It fails §1's
third condition on the ordering principle above: *"regenerated by script, so no
prose"* is a statement about how they are produced today, not an invariant the
format enforces, and nothing mechanically rejects a hand-added header. §4 already
solves the measured problem — machine identifiers ignored, authored text watched —
so the narrower rule takes it.

**Not proposed for exclusion, though it would be tempting:** `selfhost/evidence/`
as a whole. Those `.txt` and `.md` verdicts are **authored** — they are the
project's reasoning, and their spelling is exactly what a gate should watch.
Excluding the directory would buy ~314 findings and blind the most-read prose in
the repo.

### §2 — Dictionary

**Admission test:** stable project or domain vocabulary that **should remain
spell-checked in context** — a real identifier or term that recurs, not a
one-off. Per `CLAUDE.md`: inline for one or two files, global config beyond.

The point of preferring dictionary over exclusion is that a dictionary keeps the
surrounding prose checked. `tpool` in the global list still leaves every other
word on that line watched; `ignorePaths` on the file would not.

**What this category must not become:** a way to reach zero. A word enters
because it is correct vocabulary, never because it is in the way.

### §3 — Accepted spelling variants

> **Standard British and American spelling variants are not spelling defects.
> Project terminology remains governed separately by the dictionary (§2).**

**Corrected 2026-08-16.** This section previously read the config's `analysed` /
`behaviour` / `synthesised` entries as establishing *"this fork uses British
English"*. They do not. They establish only that British variants **occur** and
should not be treated as defects — which says nothing about whether American
variants should become wrong. Turning the former into the latter would be a
**style migration disguised as spelling cleanup**, decided under cover of a
cleanup task and scoped by whoever happened to run it.

If the project later wants a single editorial dialect, that is a separate
decision with its own scope. cspell promotion must not make it silently.

**Mechanism, verified before being proposed:**

```yaml
language: "en,en-GB"
```

Tested on a sample carrying both columns — `behaviour behavior analysed analyzed
organisation organization initialised initialized normalise normalize licence
license` — **all accepted**, while `delibrate` on the next line was still caught.

Two properties that matter. It resolves all **237** findings without adding a
single dictionary entry, so the dictionary stays what §2 says it is: project
vocabulary. And acceptance is per-word, not per-line — `behaviour` becoming
acceptable does **not** make an unrelated typo beside it invisible, which is the
whole reason to prefer this over exclusion.

### §4 — `.patch` files: line-scoped, comment-aware

The first version of this section proposed ignoring **every** diff-body line
(`/^[-+ ].*$/gm`) and named its own counterexample as hypothetical: *"a patch whose
authored prose is written inside the diff."* **Measured, that counterexample is
the common case, not an edge one.**

| measurement | |
|---|---|
| authored comment lines added by this repo's own patches, living in diff bodies | **1,775** |
| current baseline findings on those comment lines | **46** |

So the broad rule would have hidden 46 findings that exist **today**, plus all
future spelling in 1,775 lines of prose this project wrote. It was too wide, and
it was too wide for exactly the reason §1's third condition exists.

**The rule identifies machine content structurally instead** — code lines carry
identifiers, comment lines carry prose:

```yaml
overrides:
  - filename: "**/*.patch"
    ignoreRegExpList:
      # Ignore diff-body lines ONLY when they carry no comment marker.
      - "/^[-+ ](?![^\\n]*(?:\\/\\/|\\/\\*|^\\s*\\*\\s|#\\s))[^\\n]*$/gm"
```

**Verified before proposing it**, on a specimen holding all three kinds:

```
sample.patch:1:24 - Unknown word (delibrate)  <- authored HEADER, caught
sample.patch:8:34 - Unknown word (mispelled)  <- authored COMMENT inside the
                                                 diff body, caught
                                              <- oldvarr / newvarr /
                                                 compyler_thing / zzq /
                                                 unrelatedd_identifier in diff
                                                 CODE lines, ignored
```

Effect on the baseline: of 178 patch findings, **8 headers** and **46 diff-body
comments** stay visible; **124 diff-body code lines** are absorbed.

**KNOWN COVERAGE BOUNDARY, recorded rather than forgotten.** Diff-body *code*
lines are unwatched, and "has no comment marker" is a proxy for "is machine
content", not a proof of it. Two consequences to carry:

* **if authored prose is ever introduced inside a diff body outside a comment,
  this override must be reconsidered before that content is accepted.** A patch
  that adds a user-facing string, an error message, or documentation as code is
  exactly that case;
* the ideal mechanism identifies generated diff lines structurally rather than
  by marker heuristics. This is the closest available today and it is a heuristic;
  it is written down as one so nobody later mistakes it for a guarantee.

### §5 — Default: stays visible

**Anything that does not cleanly pass exactly one test above stays a finding.**
It is reported, not reclassified. A residue of genuinely unclassified findings is
an acceptable outcome and a better one than a forced fit: the tree-wide gate can
be promoted with a small reviewed residue cleaned by hand, but it cannot be
promoted honestly if the residue was hidden.

## The negative control protocol — per exclusion, before it is applied

Every proposed exclusion gets its own control **before** it goes in the config.
The control tests the **boundary**, not the count:

1. place a deliberate typo in content that **should remain visible**, adjacent to
   the excluded material — same directory for a path exclusion, same file for the
   `.patch` override;
2. place a deliberate typo **inside** the excluded material;
3. run the exact promoted command shape (§17's guard rule: the shape, not the
   tool);
4. **require** the adjacent typo to be reported and the excluded one not to be.

An exclusion whose control cannot show the adjacent typo being caught is too
broad and does not go in. Falling counts are not evidence: a rule that hides
everything also hides the finding you wanted.

## What this document fixes about the order of work

With these boundaries settled, step 1 is mechanical classification against a
written test. Without them, every ambiguous finding is a small policy decision
made under pressure from a visible number — and the number always argues for the
broader rule.
