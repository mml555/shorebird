VERDICT
-------
**Rows 1 and 2 PASS outright. Row 3's operative requirement — the assertion path
refuses instead of asserting a confident identity — is MET, on an in-range slot
holding a different object, which is exactly the hazard it was written to catch.
Its companion clause is vacuous because the derived scan found nothing to
locate.**

The instrumentation is therefore ESTABLISHED for the purpose the precommit
names: a supplied offset can no longer masquerade as a measurement, and the
derived scan is a real, independent producer. It is NOT established that the
derived scan reports the right slot when there is one.

This is not "instrumentation works" without qualification, and it is not the
PARTIAL the precommit warned of either — row 3 ran, on the value specified, and
returned a named refusal.

WHAT 0013 CONTRIBUTED, AND WHY THE ROW WOULD OTHERWISE HAVE BEEN UNRUNNABLE
----------------------------------------------------------------------------
0012 deleted the `0xd4a8` / "RouteBThing.value" landmine correctly, but that
special case was the only path that ever passed a non-zero `pool_offset`, and
`runtime/lib/object.cc:1257` gates the assertion on `pool_offset != 0`. On the
tree as captured there was one call site, its argument a literal `0`, no env var
and no second caller — verified, not assumed. Row 3 could not have fired at all,
and this cycle would have returned rows 1 and 2 and been reported as PARTIAL.

`0013-routeb-assert-offset-supply.patch` restored the supply side as a default
(`0xd4a8`, the value the control is specified against) plus a per-run sidecar
override, applied to every target rather than one hard-coded selector. The
override was NOT needed: `0xd4a8` landed in range on release 96. It remains the
recovery path if a future release puts it out of range.

ADDENDUM, 2026-08-17 — THE SECOND NAMED ROW-3 OUTCOME, ON A SECOND SPECIMEN
----------------------------------------------------------------------------
Added after the release 91 hybrid run (r91_vs_r96_tpool_verdict.txt). It
strengthens row 3 and changes NOTHING about the limitation below.

Row 3 named two acceptable failure shapes: `POOL_ENTRY_NOT_FUNCTION` **or**
`pool_entry_equals_target=0`. Release 96 produced the first. Release 91 produced
**the second**, from the same stale `0xd4a8`:

    release 96   pool_status=4  pool_entry_is_function=0  pool_entry_equals_target=-1
    release 91   pool_status=5  pool_entry_is_function=1  pool_entry_equals_target=0

On release 91 the stale offset landed on index 6803 holding a **real Function**
— and the assertion path reported `POOL_READ` with
`pool_entry_equals_target=0`: *this slot holds a Function, and it is NOT your
target.* That is the confident-wrong-answer hazard in its most dangerous form —
a plausible, correctly-typed object — identified as not-the-target rather than
reported as an identity.

**Both named outcomes of the negative control are now demonstrated, on two
different snapshots, from the same supplied constant.** The demotion is exercised
across its full specified range.
