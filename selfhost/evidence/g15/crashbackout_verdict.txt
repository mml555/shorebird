WHAT IT MEANS
-------------
`last_booted_patch: 1` with `boot_attempt_count: 0` is unambiguous: the boot was
recorded as a SUCCESS, three times over, while Dart was in fact failing every time.

So `Engine::Run` returns `RunStatus::Success` even when `main()` throws. Run reports
that the entrypoint was successfully INVOKED; what the isolate does afterwards does
not change its return value. Patch `0009` therefore banks success at a point that is
still too early to see a Dart-phase failure — a narrower version of the very defect
it was written to fix.

`0009` moved the seam from "the VM object exists" (the Shell constructor) to "the
entrypoint was invoked" (Engine::Run returning). That is strictly better, and it is
NOT far enough: both are before the patched Dart has demonstrated it can run.

WHAT THIS DOES AND DOES NOT OVERTURN
------------------------------------
* ARM 2 STILL STANDS. It tested the ambiguous path — no outcome reported, counter
  decides — and that path works: a good patch killed mid-boot was retried rather than
  tombstoned, twice, corroborated by the device's own state. Nothing here touches it.
* §15's gate "a Dart-phase crash backs the patch out" is **NOT closed** and must not
  be marked so.
* The three-outcome table's middle case (backout via the COUNTER after two crashes)
  did NOT occur either — the counter never ticked, because each boot was recorded as
  a success. So it is not that the mechanism is slower than intended; it is that the
  failure is invisible to it.

WHERE THE SEAM ACTUALLY BELONGS
-------------------------------
The property that must be proven before banking success is "patched Dart RAN and did
not fail", and no point inside `Engine::Run` can prove it, because `Run` returns as
soon as the entrypoint is invoked. Candidates for the next design pass, none verified:

  * after the root isolate's first message-loop turn completes without an unhandled
    error — i.e. hook the isolate's unhandled-error port rather than Run's status;
  * `Dart_SetUnhandledExceptionCallback`-style reporting, so a Dart-phase failure
    reports FAILURE positively rather than being inferred from silence;
  * first frame — REFUTED earlier for widening the false-backout window, but that
    objection was answered by `0010`'s counter, so it deserves re-examination rather
    than being treated as closed.

The last one is worth stating plainly: the adversarial review that killed first-frame
was right about the risk and the risk is now MITIGATED by the counter this same
session added. A design decision made before a mitigation existed should be re-opened
once it does.

CONTROL NOT RUN
---------------
That the PATCH causes the crash is inferred, not directly controlled: the same
