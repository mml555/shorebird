THE AUTH BLOCKER, WHICH IS A SELF-HOSTING DEFECT IN ITS OWN RIGHT
-------------------------------------------------------------------
Cutting `1.0.4+1` failed twice before it succeeded, and neither failure was about
G15:

1. `Unknown jwt issuer: http://169.254.189.3:18080`. The credential's `iss` is the
   container's `SHOREBIRD_JWT_ISSUER`; `shorebirdEnv.jwtIssuer` derives from
   `base_url` (`10.0.0.7`). Cleared by exporting `SHOREBIRD_JWT_ISSUER`.
2. `Failed to refresh credentials.` — the log shows
   `POST https://auth.shorebird.dev/token` → 401 `invalid_grant`. **The vendored
   CLI was refreshing a self-hosted credential against UPSTREAM's auth service.**
   Releases 89-92 succeeded earlier only because the access token had not yet
   expired.

Cleared WITHOUT re-syncing the CLI, by `AUTH_SERVICE_URL=http://10.0.0.7:18080`,
which `ba4e1c02` already honours (`shorebird_env.dart:263`) with the upstream URL
only as a fallback. Credit to the G4.1c lane, which read the failing call site
(`auth.dart:155-180`, `authBaseUrl: _authServiceUri`) and proposed it; it was
verified here before use, and it is what preserved this gate's CLI-constant
control.

So the full incantation for a self-hosted release on this rig is:

    export FLUTTER_STORAGE_BASE_URL=http://localhost:8085
    export SHOREBIRD_STORAGE_BASE_URL=http://localhost:8085
    export SHOREBIRD_STORAGE_BUCKET=download.shorebird.dev
    export SHOREBIRD_JWT_ISSUER=http://169.254.189.3:18080
    export AUTH_SERVICE_URL=http://10.0.0.7:18080
    shorebird release ios --export-method development

The underlying defect — a vendored CLI that cannot refresh a self-hosted
credential without two env vars — is real and is fixed at HEAD (`b7779960`,
`86d4390d`, `53b332f8`). It is not a G15 finding and is recorded here only
because it will stop the next person too.
