WHAT THIS LOOKS LIKE, AND WHY IT IS NOT ASSERTED
--------------------------------------------------
This is the signature of the defect `probes/assert_result_consumed.sh` was
written for and which `PARITY.md` records as the FIFTH CORRECTION: the call is
emitted and runs, but its RESULT is dead, because a body returning a
compile-time constant lets type-flow substitute the constant at the call site.
`caller_scan_status=0` and every `pool_*` field at `-1` in the trace above are
consistent with that.

**It is NOT asserted, because the probe could not measure it here:**

    assert_result_consumed.sh <release App> --fixture-signature
    -> patchable sites : 12,559
       located         : 0
       RESULT: NOT LOCATED

The probe says in its own words that this is not a pass — *"a target whose call
site cannot be found is a target whose result-consumption is UNKNOWN"*. Its
`--fixture-signature` locator was written for a different fixture's shape and
does not match `killswitch_app`'s. So the leading explanation is unconfirmed and
is recorded as a lead.

**And there is a counter-observation that must not be dropped:** the SAME target,
`routeBValue`, DID show `NEW-kill` on this fixture on 2026-08-14
(`arm2_verdict.txt`, release `1.0.2+1`, cell `80e493e4`). If the call site were
unconditionally constant-folded, that could not have happened. So something
changed between then and now — candidates, all untested: the new cell
`cd137db6` (patch `0011`), the CLI at `98f84c17` (which changed what defines the
prepass and import kernels are compiled with), or the rebuilt platform dill.

WHY THE GATE STOPPED HERE
--------------------------
1. **Arm A cannot be scored.** Its PASS row requires `NEW-kill` on screen. Its
   FAIL row requires `Bad{BootCrash}`. Neither holds.
2. **Reporting it as a pass on the updater state alone would be exactly the error
   this project keeps paying for** — `last_booted_patch: 1` with no tombstone is
   the flattering half, and the specimen's own claim is absent.
3. Arms B and C were not run. **Arm B does not obviously share the defect** — it
   tests a THROW, and exception propagation does not depend on whether a return
   value is consumed — but running it before arm A is understood would spend a
   device cycle on a gate whose first arm is unexplained.

None of that is arm A's claim, and none of it is reported as such.
