`param=PARAM-ARG` is the value the arm predicted. It proves nothing, because the
bundle that produced it was NOT release 37.

  preserved release 37   LC_UUID 31869a1e971e37e085c8646ab2627e61
  bundle actually run    LC_UUID 2da6f295023933b895815c59e4de98e9

`shorebird patch ios` re-archives over `build/ios/archive`, and that archive is the
PATCH BUILD: the edited source compiled straight into a fresh AOT binary. So
`paramValue` returned 'PARAM-ARG' natively, with the interpreter, the bytecode
container and the whole patch mechanism playing no part. This is the rig's strongest
possible false positive, and it agrees with the arm's prediction exactly — which is
what makes it dangerous rather than merely wrong.

THE TELL WAS ON THE SAME LINE. `code_patch=none` reads
`widget.runtime.patchNumber`, the updater's active patch. A patched device cannot
report `none`. The corroborating row contradicted the headline row, and that is what
prompted the identity check.

THE GUARD ALREADY EXISTED, IN TWO PLACES

  * PARITY.md:1417 — "the patch build re-archives over build/ios/archive, so after
    patch 1 the archive holds the patch build"
  * airgap_acceptance.sh `launch_fixture` — ten lines on exactly this, ending
    "Installing the patch build instead would display the patched value with the
    patch mechanism playing no part -- the strongest false positive this rig can
    produce"

Both were bypassed by hand-rolling `ios-deploy --bundle <archive>/Runner.app`
instead of going through `launch_fixture`. `assert_installed_release.sh` was run,
and passed — BEFORE the patch build, when the archive was still the release. A
correct check at the wrong moment.

The response is therefore not another note. `probes/launch_release_bytes.sh` makes
identity a precondition of LAUNCHING: it takes the release number, resolves the
.ipa (which the patch build leaves alone), compares against this directory's
LC_UUID, refuses on mismatch, and names the archive's differing UUID out loud.
