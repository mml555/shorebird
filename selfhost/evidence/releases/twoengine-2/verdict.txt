WHAT THIS SETTLES

Patch `0007`'s fix works on hardware. The pre-`0007` symptom was engine two
silently running unpatched AOT: arming sat below an early return gated on an
updater init that deliberately fails on its second call, so `ConfigureShorebird`'s
second invocation never reached `InstallRouteBActivationHook`. Two records with two
distinct `Function`s is that path executing twice.

And the mechanism claim is now proven at all three layers, each independently:

  * structural host   — two engines really are two engines (`evidence/g15/`, stock
                        Flutter, `arming_observed=0` by construction)
  * this gate         — both engines arm on the shipping engine

A REAL HARNESS DEFECT: THE SCREEN WAS BLACK — ROOT-CAUSED AND FIXED SAME DAY

Engine one's UI does not render — the screen is black while the app runs, not the
indigo `_HarnessApp`. Confirmed by screenshot DURING a live launch, not merely
after. The window and root `FlutterViewController` are constructed from engine one,
which was already `run()` headlessly, and no frame appears.

It does not touch this verdict, and the reason is structural rather than a judgement
call:

  * the per-engine markers are written by Dart inside `_boot` BEFORE `runApp`, so
    they attest that each root isolate ran and executed `engineMark()`;
  * the `rbtrace` records are written by the ENGINE during `AttachBytecode`;
  * `mark=MARK-PATCHED` in both markers is the patched body's RETURN VALUE, which
    requires execution, not display.

Nothing in the chain passes through rendering.

**ROOT CAUSE: the app was SCENE-based.** `flutter create` emits
`UIApplicationSceneManifest` naming a `SceneDelegate` *and a second storyboard
reference* (`UISceneStoryboardFile = Main`). When a scene manifest is present the
SCENE owns the window, so the `window` this host assigns in
`didFinishLaunchingWithOptions` is ignored. Deleting `UIMainStoryboardFile` had
removed only ONE of the two storyboard routes.

**FIXED** — `prepare_twoengine_fixture.sh` now deletes the scene manifest too,
returning UIKit to the legacy delegate window lifecycle that this host implements.
Verified on the simulator: the indigo `ENGINE one` screen renders with its identity
line, both engines still boot, and `implicit_engine=0` still holds — in fact more
strongly, since the scene config was the last route to an implicit engine.
Evidence: `evidence/g15/render-after-scene-fix.png`,
`evidence/g15/host-after-scene-fix.marker`.

Also fixed while here: the host's `reason=` string, which said
`stock_engine_simulator_structural_only` even on a device run against our engine. It
is now `host_does_not_observe_arming`, which is true in every context — the host
cannot know which engine or platform it is on.

ONE WORDING DEFECT IN THE HOST MARKER, recorded rather than hidden

`device-host.marker` reads `arming_observed=0
reason=stock_engine_simulator_structural_only`. The first half is TRUE and
important — the host does not observe arming, so its four findings are about
construction and boot only. The reason text is stale in this context: this run is
our engine on a device, not stock Flutter on a simulator. The host cannot know
which it is, so the reason should be context-free
(`reason=host_does_not_observe_arming`). It changes no verdict here, because the
arming evidence comes from the trace and the markers' `mark=` field, neither of
which the host writes.
