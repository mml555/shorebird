# flavored_probe — the flavored acceptance fixture

One app, two flavors (`foo`, `bar`), one `app_id`. It exists so `G4.2`'s device
arms can be constructed at all: `airgap_app` has no schemes, no flavored
configurations and one bundle id, so `--flavor` cannot be built there.

**A second fixture on purpose.** Adding flavors to `airgap_app` would revise the
shape of the binary that every banked Route B device result refers to, and it
would spend the `R6` release counter that the canonical fixture owns. PARITY §16
asks for a second fixture; this is it.

## What is committed vs generated

| committed | generated by `selfhost/scripts/prepare_flavored_fixture.sh` |
|---|---|
| `pubspec.yaml`, `pubspec.lock` | `ios/`, `android/` (from `flutter create`) |
| `lib/main.dart`, `assets/probe.json` | `shorebird.yaml` (from the template) |
| `shorebird.yaml.template` | `.generated/shorebird.<arm>.yaml` |
| `ios_overlay/`, `android_overlay/` | `test/`, `analysis_options.yaml`, IDE files |

The overlay is committed and the tree it is applied to is not: that tree belongs
to the pinned Flutter's generator, so it is gated by a recorded sha
(`ios_overlay/BASELINE.project.pbxproj.sha256`) rather than by review. A mismatch
means the overlay was derived from a different generator and must be **refused**,
not overlaid.

## Design decisions with reasons, because each one reads as an omission

**No plugins.** No `code_push_runtime`, no `dynamic_modules`. Zero plugins means
no `Podfile`, and this fixture adds **six** build configurations — under CocoaPods
each needs its own generated `Pods-Runner.<configuration>.xcconfig`, and a missing
one fails as *"CocoaPods did not set the base configuration"*, which reads as a
defect in the flavor overlay and is not one. Adding the dependency later is a
pubspec line plus a re-run; removing it after six configurations carry pod
includes is not.

**Two readings, never one.** `flavorState()` reports the flavor the compiler was
given; `kReleaseState` reports which BUILD is running and a patch flips it to
`V2`. Keeping them separate is what prevents a matching-flavor arm from passing
because the release already said what the patch would say — the exact false
positive that cost a discarded run on 2026-08-13
(`evidence/releases/37/DISCARDED-2026-08-13.txt`).

**Every asserted value is displayed, not just beaconed.** The control plane logs
the beacon's query string for that path (`loggedRequestPath`), so the beacon works
— but when iOS Local Network consent is missing the beacon cannot send at all, and
a displayed row still separates "the app ran and shows the release value" from
"the app never ran".

**All flavors map to one `app_id`.** With distinct ids, `patch --flavor bar`
resolves a different app and fails *"release not found"* before any flavor
fingerprint is compared — a refusal for the wrong reason, which would bank a green
arm for a mechanism that never ran. See the comment in `shorebird.yaml.template`.

**Three handling rules, from
`../../evidence/g42_flavored_fixture/h2_step7_supplement.txt`:**

1. **Count with `grep -c`, never `grep -xc`.** `flavorState()` has two branches,
   so the binary carries `V1/Foo` *and* `V1/Foo!`; `-x` matches whole lines and
   silently reports half the count.
2. **Every flavor builds to `Runner.app`** — there is no `flavored_probe_foo.app`,
   in any directory. The xcconfigs' `PRODUCT_NAME` is inert (the pbxproj sets it
   18 times and wins), so all arms overwrite one path. Run each arm cold, and
   never read sha equality between arms as a result: it is a build-cache hit.
3. **`assert_result_consumed.sh` has not passed here** — exit 2, NOT LOCATED,
   under every locator tried, because `flavorState()` is reached by a direct `bl`
   and the gate inventories only indirect pool-load dispatch. That is MEASUREMENT
   INCOMPLETE and is owed *before* any device arm is read, not after.
