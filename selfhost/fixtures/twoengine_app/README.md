# twoengine_probe — the two-engine harness

`G15`'s device gate asks whether **engine two is armed at all** when one process
holds two `FlutterEngine`s. Nothing in this repo could ask that question: every
fixture boots one engine. This is the missing precondition, and nothing more.

**A clone, not an edit.** `airgap_app` is `R6`, "the sharpest serializer", whose
`shorebird.yaml`, version and `main.dart` are per-run mutable state; a goal needing
its own fixture does not contend on it at all. That is what lets this lane run
beside the flavored fixture's.

## What is committed vs generated

| committed | generated by `selfhost/scripts/prepare_twoengine_fixture.sh` |
|---|---|
| `pubspec.yaml`, `pubspec.lock` | `ios/` (from `flutter create`) |
| `lib/main.dart` — two entrypoints | `ios/Runner/AppDelegate.swift` (copied from the overlay) |
| `ios_overlay/AppDelegate.swift` — the host | `ios/Runner/Info.plist` edits (see below) |
| `shorebird.yaml.template` | `shorebird.yaml` |

`ios/` is gitignored, so a host edited in place is deleted by the next
materialize. The overlay is the source of truth and the script re-applies it —
the same re-injection pattern `prepare_airgap_fixture.sh` uses for its two
Info.plist keys.

## The three shapes this harness refuses

**A third, implicit engine.** `UIMainStoryboardFile = Main` makes the generated
Runner boot its own engine; construct two more and the process holds three, so no
per-engine reading is attributable. The script deletes that key, and the host
keeps `didInitializeImplicitFlutterEngine` as a **tripwire**: if it ever fires the
harness shows a red refusal screen and constructs nothing, because a three-engine
process is a broken harness rather than a finding about arming.

**A shared `FlutterDartProject`.** `FlutterEngine` copies `[self.dartProject
settings]` into the Shell, so a shared project hands engine two an
*already-armed* callback and it runs patched code even without patch `0007` — a
false pass. Each engine gets its own project, which also means two
`ConfigureShorebird` calls, and the second is exactly the case `0007` fixes.
There is deliberately **no fallback** that retries with a shared project: if only
that shape boots, the run must fail rather than degrade into the shape that always
looks green. For the same reason, never `FlutterEngineGroup` and never
`spawnWithEntrypoint`.

**Unattributable output.** Each engine runs a distinct entrypoint, prints a
distinct prefix, and writes its own marker file. `engineTwoMain` carries
`@pragma('vm:entry-point')` because without it the entrypoint survives
`flutter run` (JIT keeps everything) and is tree-shaken in AOT — it would work all
through development and fail in the release-mode gate this exists to unblock.

## Measured once, on the simulator — 2026-08-13

Stock Flutter 3.44.8, iPhone 17 Pro simulator. Preserved at
`selfhost/evidence/g15/`:

```
host.marker    implicit_engine=0
               projects_distinct=1 p1=13142886284893985144 p2=11267730310750048978
               engines_constructed=2 engine_one_run=1 engine_two_run=1 engines_distinct=1
               arming_observed=0 reason=stock_engine_simulator_structural_only
engine-one     engine=one isolate=main          entrypoint=main
engine-two     engine=two isolate=engineTwoMain entrypoint=engineTwoMain
```

Each entrypoint logged exactly once; the two Dart markers differ byte-wise.

**The host findings are in a FILE, not the log, and that was measured too:**
`NSLog` from a simulator app reaches neither `flutter run`'s output nor
`xcrun simctl spawn <udid> log show`, while the Dart side's `print` arrives fine.
Host facts logged that way would simply be unobservable.

## What this does NOT claim

`arming_observed=0`, stated by the host itself. This runs on **stock** Flutter, so
it cannot observe Route B arming even in principle, and a green run here must
never be reported against `G15`. Construction/boot success and arming state are
separate observations. The arming contract's own evidence is separate as well —
patch `0008`'s three host unit tests — and neither result implies the other: a
simulator failure would not invalidate those tests, and passing tests say nothing
about second-engine behaviour.

**Known, and it will matter at the device gate:** `RouteBReport` appends to
`artifact_path + ".routeb"`, and both engines resolve the same lifecycle-selected
path, so **both engines write one file**. Release 32's real specimen is four lines
with no engine discriminator. The discriminator to lean on is the sibling
`.routeb.trace`: release 32's carries exactly one `rbtrace v=4 … fn=0x…` line, so
two attaches in one process should give **two**. Their `fn=` values are *predicted*
to differ, since each engine has its own isolate and heap-allocated `Function` —
never measured, so identical `fn=` is something to investigate, not an automatic
failure. Writing this down now is what stops a later reader taking "one block" as
"engine two unarmed" when it may mean "engine two never booted".
